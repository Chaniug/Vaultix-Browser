# 02 · 工程规范与门禁

> 配套 `01-开发硬性规约.md`。`01` 管"不能做什么"，本文管"怎样算做完了"。

## E. 代码与目录（E 系列）

### E-1 TypeScript strict
- 禁止隐式 `any`；确需逃逸用 `// @ts-expect-error: <理由>`，无理由的豁免 CI 拒绝。

### E-2 目录结构（依赖方向单向）
```
src/
  core/          # 统一模型、契约、后端无关逻辑（不依赖任何适配器）
  adapters/
    bitwarden/   # 实现 core 定义的接口
    keepassrpc/  # 实现 core 定义的接口
  ui/            # popup / options，只依赖 core
  content/       # content script，只做 DOM 识别与填充
  background/    # service worker，组装适配器并注入
  shared/        # 类型、常量、日志封装
```
- **依赖方向**：`ui / content / background → core ← adapters`；`ui / content` **禁止 import 具体适配器**。
- **理由**：换后端不动 UI，是"双源一层抽象"的物理保证。
- **验证**：ESLint `no-restricted-imports` 规则。

### E-3 命名
- 类型 `PascalCase`、函数 / 变量 `camelCase`、常量 `UPPER_SNAKE_CASE`、文件 `kebab-case`。

### E-4 适配器封装
- 每个适配器独立目录，对外只暴露 `factory + 接口实现`，内部结构自由。

### E-5 工具配置入库
- ESLint / Prettier / tsconfig 配置提交到仓库，禁止个人本地配置覆盖。

## F. 测试（T 系列）

### T-1 加密 / 协议逻辑必须有测试向量
- 不能只测"不抛异常"，要有"已知输入 → 已知输出"。
- KeePassRPC：用公开协议文档里的示例向量。
- Bitwarden：用官方测试向量 + bw2keepass 已验证样本。

### T-2 兼容性测试矩阵
- Bitwarden：官方云 / Vaultwarden 两种 base URL 的配置层测试（DEC-002 的验收手段）。
- KeePassXC：不同版本的协议能力差异至少覆盖配置层。

### T-3 填充 DOM 测试
- 覆盖普通表单、Shadow DOM、动态加载表单（SPA 常见）。

### T-4 锁定策略状态机测试
- 含 service worker 被回收的模拟场景。

### T-5 准入门槛
- 新增功能无测试不合并；bug 修复必须附回归测试。

## G. CI 门禁（G 系列）

> **铁律：七道门禁分开单跑，禁止用 `&&` 串成一条命令。**
> 理由：串起来会在中间失败时掩盖后面环节的状态，且无法一眼定位挂在哪一关（既有项目教训）。

| 门禁 | 检查内容 | 失败处理 |
|---|---|---|
| G1 | TypeScript 编译 / typecheck | 阻断合并 |
| G2 | ESLint + Prettier check | 阻断合并 |
| G3 | 单元测试（Vitest） | 阻断合并 |
| G4 | 安全静态扫描（敏感 API、console、HTTP、权限白名单） | 阻断合并 |
| G5 | 依赖许可证检查（L-1） | 阻断合并 |
| G6 | 构建产物检查：manifest 断言 + 无远程代码 + 体积阈值 | 阻断合并 |
| G7 | DOM / 填充集成测试 | 阻断合并 |

- **本地开发**：可只跑相关门禁。
- **PR 合并**：CI 七道全绿，缺一不可。
- **理由**：门禁是"避免跑偏"的执行层——文档写了不做 X，G4 就得把 X 拦下来。

## H. 文档（D 系列）

### D-1 分篇原则
- 入口文件（`README.md` / `docs/README.md`）只放指针 + 当前状态；细节按篇，不堆长文。

### D-2 单篇超过 200 行必须拆分

### D-3 决策记录格式固定
- `问题 → 选项 → 结论 → 理由`，追加到对应文档末尾，**不单开文件**。

### D-4 禁止裸 TODO / FIXME
- 必须带 owner 和 issue 链接。

### D-5 状态表必须与实现一致
- 改了实现就更新 README 和 `docs/README.md` 的状态列。

## I. 提交与版本（V 系列）

### V-1 Conventional Commits
- 类型：`feat` / `fix` / `chore` / `docs` / `test` / `refactor` / `security`。

### V-2 破坏性变更
- 在 commit message 与 PR 标题标注 `BREAKING CHANGE`。

### V-3 版本号
- 语义化版本；P0~P3 期间用 `0.x`，双源契约稳定后升 `1.0.0`。

### V-4 分支策略
- 不在 `main` 上直接提交；走分支 + PR + 门禁 + 合并。
