# 03 · 统一契约

> P0 契约。定义 `CredentialItem`（统一条目模型）与 `BackendAdapter`（后端适配器接口）。
> **代码即契约**：真实签名在 `src/core/types.ts` / `src/core/merger.ts`，本文说明设计意图。字段变更须先改本文（C-1）。

## 1. 设计目标

两个后端返回的数据形状差异很大：

| 字段 | Bitwarden（解密后 Cipher） | KeePassXC（get-logins） |
|---|---|---|
| 标识 | `id` (UUID) | `uuid`（协议响应可选带） |
| 名称 | `name` | `name` |
| 登录名 | `login.username` | `login` |
| 密码 | `login.password` | `password` |
| 过期 | 无 | `expired` |
| TOTP | `login.totp` | 需单独 `get-totp` |
| URI 匹配 | `login.uris[]` + 匹配策略 | 桌面端已按 URL 匹配，不回传 URI |
| 自定义字段 | `fields[]` | 不回传 |
| 备注 | `notes` | 不回传 |

**结论（D-01）**：不做交集（会丢 TOTP / 自定义字段），做**核心必填 + 可选增强 + meta 逃生舱**的联合模型。

## 2. CredentialItem 分层

```
核心必填（两个后端都保证）
  id · source · name · username · password
       ↓
可选增强（按 capabilities 填充，缺失不崩）
  totp · uris · customFields · notes · expired
       ↓
meta（来源特有原始数据，UI 不得依赖结构）
```

### 字段语义

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `id` | `string` | 双方 | 后端内唯一标识 |
| `source` | `'bitwarden' \| 'keepassxc'` | 适配器层写入 | **readonly**，UI / content 只读（S-6） |
| `name` | `string` | 双方 | 显示名 |
| `username` | `string` | 双方 | 登录名 |
| `password` | `string` | 双方 | 明文，**仅内存态**，不落盘不打印（S-1/S-2） |
| `totp?` | `string` | Bitwarden 直给 / KeePassXC 需二次请求 | 能力见 `capabilities.totp` |
| `uris?` | `CredentialUri[]` | Bitwarden | KeePassXC 由桌面端匹配，此处留空 |
| `customFields?` | `CustomField[]` | Bitwarden | 类型对齐 text/hidden/boolean/linked |
| `notes?` | `string` | Bitwarden | — |
| `expired?` | `boolean` | KeePassXC | UI 应警示 |
| `meta?` | `Record<string, unknown>` | 双方 | 逃生舱，UI 禁止依赖（C-2） |

> `exactOptionalPropertyTypes: true`：可选字段未设置时必须是 `undefined`，不能用 `null` 占位。这是刻意的严格约束。

## 3. BackendAdapter 接口

```ts
interface BackendAdapter {
  readonly source: BackendSource;
  readonly capabilities: BackendCapabilities;
  isReady(): boolean;
  search(query: SearchQuery): Promise<readonly CredentialItem[]>;
  listAll(): Promise<readonly CredentialItem[]>;
}
```

**实现纪律**：
- `search` 不得向调用方抛异常 → 内部消化、返回空数组、日志脱敏（S-2）。
- `source` 必须是字面量常量，合并器会校验条目 `source` 与适配器声明一致（S-6）。
- `listAll` 在能力不支持时返回空数组，UI 按 `capabilities.listAll` 决定是否展示"全部条目"。

### BackendCapabilities（C-3）

| 能力 | Bitwarden | KeePassXC | UI 行为 |
|---|---|---|---|
| `search` | ✅ | ✅ | 都支持按 URL 查 |
| `listAll` | ✅ | ⚠️ 需 get-database-groups 遍历 | 不支持则隐藏入口 |
| `totp` | ✅ | ✅（get-totp） | 决定 TOTP 按钮 |
| `customFields` | ✅ | ❌ | 决定自定义字段区 |
| `uriMatching` | ✅ | ❌（桌面端代劳） | 决定 URI 匹配设置项 |
| `write` | ✅（P4） | ✅（P4，set-login） | 用户确认后写回后端，见 DEC-010 |

## 4. 双源合并策略（D-02 落地）

实现在 `src/core/merger.ts: searchAcrossBackends()`：

1. **按优先级排序**：默认 `['bitwarden', 'keepassxc']`，用户可在设置里改。
2. **不弹窗**：同 URL 多来源命中时，取优先级最高者填充，`ambiguous: true` 仅作为标记。
3. **UI 自主决定**：标记为真时，popup 可显示轻量来源切换提示（非模态、不阻塞填充）。
4. **容错**：单个后端未就绪或抛错 → 跳过，不影响其他来源。
5. **防伪造**：丢弃 `item.source !== adapter.source` 的条目。

### SearchQuery

```ts
interface SearchQuery {
  readonly url: string;          // 当前页面完整 URL
  readonly submitUrl?: string;   // 表单 action，可选
  readonly httpAuth?: boolean;   // HTTP Basic Auth 场景
}
```

## 5. 依赖方向（E-2）

```
content ─┐
   ui ───┼──→ core (types / merger) ←── adapters
background ┘
```

- `core` 不 import 任何具体适配器，也不 import 浏览器 API。
- `ui` / `content` 只依赖 `core`，禁止 import `adapters/*`（ESLint `no-restricted-imports` 将落地）。
- `background` 是唯一组装点：创建适配器实例 → 注入合并器 → 提供给 UI。

## 决策记录

### DEC-005 · D-01 统一模型以"核心 + 可选 + meta"为准
- **问题**：KeePassXC 只回三字段，Bitwarden 字段丰富，以谁为准？
- **选项**：A 取交集 / B 联合类型 + source 标记 / C 只做 Bitwarden 模型
- **结论**：B，采用分层模型，不丢字段。
- **理由**：卖点是"两个库统一管"，取交集等于自废武功；分层让 UI 能优雅降级。

### DEC-006 · D-02 冲突处理用优先级，不弹窗
- **问题**：两库有同一域名账号时怎么办？
- **选项**：A 默认优先某一库 / B 每次弹窗让用户选 / C 设置里配优先级
- **结论**：C，默认 Bitwarden 优先；`ambiguous` 标记供 UI 轻量提示，不阻塞填充。
- **理由**：弹窗破坏填充体验（用户装插件就是为了少点）；但完全不提示会掩盖歧义，故留标记。

### DEC-007 · D-03 首版浏览器范围锁定 Chrome / Edge
- **问题**：是否同时适配 Firefox？
- **选项**：A 仅 Chromium / B 全平台 / C 先 Chromium 后评估 Firefox
- **结论**：C。
- **理由**：MV3 在 Firefox 的 service worker 行为与权限模型有差异，首版聚焦一个目标降风险。

### DEC-011 · P4 写操作契约：CredentialDraft / SaveResult
- **问题**：写回后端需要新增什么契约？
- **选项**：A 复用 CredentialItem / B 新增草稿类型 + 保存结果 / C 不定义，适配器各自处理
- **结论**：B。新增 `CredentialDraft`（url / username / password / name? / uuid? / folder?）与 `SaveResult`（ok / source / id / created），`BackendAdapter.save(draft)` 为可选能力（由 `capabilities.write` 声明）。
- **理由**：CredentialItem 含 source/meta 等后端已分配字段，不适合做写入输入；草稿类型让 UI 只传用户可编辑字段，结果回传统一形状。来源仍由适配器写入（S-6）。

### DEC-012 · 统一填充服务：UI 不持有密码，验证码收敛为即时码
- **问题**：popup 与页面内浮层如何共用一套填充？两个库的验证码形态不同怎么办？
- **选项**：A 各 UI 自行拼装填充值 / B 由 background 统一解析，UI 只报「来源 + 条目 + 字段」
- **结论**：B。新增 `FillItemMessage`（source / id / fields）与 `FillPlan`；搜索结果对 UI 瘦身为 `Suggestion`（不含密码）。验证码统一解析为即时码：KeePassXC 现取，Bitwarden 由 `otpauth` 种子按 RFC 6238 计算。
- **理由**：此前 Bitwarden 条目的 `totp` 是 otpauth 种子，直接写进验证码框是错的；两处 UI 各写一遍必然再次分叉。收敛到一处后，`CredentialItem` / `BackendAdapter` 契约本身不变，无需迁移。
- **授权边界**：页面内浮层按站点经 `optional_host_permissions` 运行时授权（M-3），不申请全站通配权限。
