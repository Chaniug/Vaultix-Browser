# 00 · 项目章程

> 本文档是**范围宪法**：定义"要做什么"和"不做什么"。任何需求、PR、AI 生成内容与本章程冲突时，以本章程为准。
> 修改章程 = 重大决策，走"问题 → 选项 → 结论 → 理由"记录到本文末尾。

## 1. 使命（一句话）

一个 MV3 浏览器扩展，让用户在网页登录时，从**同一个入口**取用 Bitwarden 系（官方云 / Vaultwarden）与 KeePassXC 两类密码库的凭证——不装第二个插件，不记两套快捷键。

## 2. 为什么存在

- [Vaultix](https://github.com/Chaniug/Vaultix) 解决手机端，本项目补齐**桌面浏览器**端，构成同一用户的完整链路。
- 双库用户的现状痛点：两个插件、两套填充体验、两处快捷键、冲突时手动试。

## 3. 核心场景（in scope）

| 角色 | 场景 | 期望 |
|---|---|---|
| 双库用户 | 工作库在 Vaultwarden，个人库在 KeePassXC | 一个下拉框选来源，统一快捷键填充 |
| 迁移中用户 | 正从 KeePassXC 迁往 Bitwarden | 并存期不用反复切换插件 |
| 隐私敏感用户 | 自建 Vaultwarden，不信任公有云 | 明文只在内存，主密码不落盘 |

功能边界（DEC-010 修订）：**填充 + 写回**（搜索 → 匹配 → 填充用户名/密码/TOTP；表单提交后提示保存新凭证 / 更新已有凭证，写回对应后端）。P0~P3 为只读阶段，P4 起加入写操作；写操作必须经用户确认，凭证只写回后端，不在插件本地落盘（S-1）。

## 4. 明确不做（out of scope）

> 这是本章程最关键的一节。新需求命中下表时，**先改章程再动手**，不许悄悄加。

| 不做 | 理由 |
|---|---|
| 独立账号 / 同步体系 | 复用两个后端的账号体系，绝不造第三个信任根 |
| 插件本地保存明文凭证 | 违反 S-1；凭证只写回后端，会话态仅存 `chrome.storage.session`（DEC-010） |
| 完整密码生成器、Send、支付卡 / 身份条目管理 | 官方客户端做得更好；本项目聚焦"取凭证 → 填表单 → 确认后写回" |
| 在扩展内解析 / 解密 `.kdbx` | 安全与复杂度双输，走 KeePassRPC 由桌面端解密 |
| 生物识别解锁 | 浏览器无可靠统一 API；交回后端（KeePassXC 解锁 / Bitwarden PIN） |
| 同步插件自身配置到云 | 避免引入新的信任面；配置只在本地 |
| 移动端（Android / iOS）浏览器 | 由 Vaultix 负责，边界清晰 |
| i18n 框架 | 首版中文；字符串集中管理即可，不引入框架 |
| 自定义主题 | 跟随系统亮 / 暗，不做主题编辑器 |

## 5. 与 Vaultix 的边界

| 关注点 | Vaultix（Android） | Vaultix-Browser（本项目） |
|---|---|---|
| KDBX 解密 | 应用内 `kdbxweb` | **不做**，交给 KeePassXC 桌面端 |
| Bitwarden 解密 | 应用内 | 扩展内，复用官方 SDK |
| 锁定时机 | `VaultLockManager` | 复用语义，独立实现（浏览器环境不同） |
| 账号体系 | 用户自填 | 后端提供 |
| 共享资产 | 加密格式知识（见 bw2keepass）、锁定时机模型 | 同左 |

## 6. 成功标准（可衡量）

1. 用户在两个库各存一条同域名账号，装一次扩展即可分别填充，**无需第二个插件**。
2. 官方云与 Vaultwarden **同一套代码**，仅 base URL 不同 → 有自动化测试覆盖两种配置。
3. 主密码、派生密钥、明文凭证不进磁盘、日志、遥测 → 有 CI 静态检查 + 代码审查清单兜底。
4. 浏览器重启后到可填充 ≤ 3 次用户交互。
5. CI 七道门禁全绿才允许合并（见 `02-工程规范与门禁.md`）。

## 决策记录

### DEC-001 · KDBX 侧走 KeePassRPC，扩展内不解密
- **问题**：浏览器扩展如何访问本地 `.kdbx`？
- **选项**：A 扩展内选文件 + kdbxweb / B Native Messaging 桥 / C KeePassRPC（KeePassXC 桌面端）
- **结论**：C。用户拍板"推荐用户使用 KeePassXC-Browser + KeePassRPC"。
- **理由**：桌面端解密，扩展零密钥暴露；`keepassxc-proxy` 随 KeePassXC 安装，不用自写本地代理。

### DEC-002 · Bitwarden 侧复用官方内核，不 fork 官方扩展
- **问题**："把官方那一套拿过来"的边界在哪？
- **选项**：A fork `bitwarden/clients` 浏览器扩展 / B 用官方 SDK + Client API 自写薄壳
- **结论**：B。
- **理由**：Vaultwarden 维护者明确其只实现 Client API；官方云与自建共用同一 Client API，换 base URL 即可。fork 整个扩展 = 永远追不上上游。

### DEC-003 · 许可证 GPL-3.0
- **问题**：选什么协议？
- **选项**：GPL-3.0 / MIT / AGPL
- **结论**：GPL-3.0。
- **理由**：上游 KeePassXC-Browser 与 bitwarden/clients 均为 GPL-3.0，复用其代码必须同协议；与 Vaultix 保持一致。

### DEC-004 · 规约先行
- **问题**：先写代码还是先立规矩？
- **选项**：A 直接搭骨架 / B 先写章程 + 硬性规约 + 门禁
- **结论**：B。
- **理由**：用户要求"先把项目到底要干嘛、插件开发硬性要求规定好，避免以后跑偏"；AI 接力项目尤其需要可检查的边界。

### DEC-010 · 加入写回能力，但拒绝插件本地保存凭证
- **问题**：用户要求扩展作为完整填充器，需支持"保存密码"。写操作原为 out of scope；"插件本地记住"可能违反 S-1。
- **选项**：A 维持只读 / B 写回两个后端 + 本地加密缓存 / C 写回两个后端 + 会话态内存 + 用户确认提示，不本地落盘
- **结论**：C。P4 起加入写操作（Bitwarden Cipher 新建/更新、KeePassRPC set-login）；表单提交后弹确认提示。
- **理由**：真正填充器需要保存新凭证；但明文凭证落盘违反 S-1 硬红线，且会引入第三个信任面。会话态用 `chrome.storage.session`（内存）满足"下次填充少点一次"的体验，凭证本身只写回用户已有的密码库。
- **S-1 立场**：本决策不修改、不放宽 S-1；任何要求本地落盘明文凭证的实现均不得合并。
