# 01 · 开发硬性规约

> **红线清单，不是建议。** 违反任一条的代码不得合并。
> 每条格式：`规则 → 理由 → 验证方式`。CI 门禁编号 `G1~G7` 定义见 `02-工程规范与门禁.md`。

## A. Manifest 与平台（M 系列）

### M-1 必须使用 Manifest V3，禁止 MV2
- **理由**：Chrome 已停止 MV2；MV3 的 service worker 模型直接决定了密钥生命周期设计。
- **验证**：CI 断言 `manifest.json` 的 `manifest_version === 3`。

### M-2 权限白名单制，新增权限必须登记"用途 + 替代方案评估"
- **允许**：`activeTab`、`storage`、`scripting`、`nativeMessaging`、`contextMenus`、`clipboardWrite`、`notifications`、`offscreen`
- **默认禁止**：全量 `tabs`、`webRequestBlocking`、通配 `<all_urls>` 的 host 权限、`debugger`、`cookies`
- **理由**：权限即攻击面，也是商店审核重点。`activeTab` 按需授权优于宽泛 host 权限。
- **验证**：CI 解析 manifest，白名单外权限 fail；新增权限须在本文追加登记。

### M-3 host 权限精确到域名，运行时配置优先
- **规则**：Vaultwarden / Bitwarden 地址由用户在设置里填，走 `optional_host_permissions` 运行时授权；manifest 不写死任何第三方域名。KeePassRPC 走 `nativeMessaging`，不占 host 权限。
- **理由**：base URL 可变是核心需求（DEC-002）；写死域名会同时破坏功能和审核。
- **验证**：code review + CI 正则扫描 manifest 的 `host_permissions`。

### M-4 禁止远程代码
- **规则**：不得加载外部脚本、不得 `eval` / `new Function`；CSP 不允许 `unsafe-eval`。WASM 例外走 M-5。
- **理由**：MV3 硬性规定，也是"明文不出本地"的前提。
- **验证**：构建产物扫描 + CSP 断言 + ESLint `no-eval` / `no-new-func`。

### M-5 引入 WASM 依赖前必须过安全评估
- **评估项**：来源可信度、供应链、CSP 需求（优先 `wasm-unsafe-eval` 而非 `unsafe-eval`）、产物体积、能否离线构建。
- **理由**：Bitwarden SDK 很可能是 WASM；这是唯一能合法引入的"近似远程代码"路径，必须显式把关。
- **验证**：PR 模板勾选项 + 评估结论写入决策记录。

### M-6 service worker 不得作为唯一密钥宿主
- **规则**：MV3 service worker 空闲会被浏览器终止（时长因版本而异，按最短处理）。会话密钥只存在于"解锁会话"内，会话态存 `chrome.storage.session`（内存态，不落盘）；SW 被回收后若会话失效 → 提示重新解锁，**禁止静默降级为明文缓存**。
- **理由**：SW 生命周期不由我们控制；把密钥只放 SW 等于随机丢密钥。
- **验证**：`07-锁定与安全.md` 的生命周期测试用例 + 代码审查。

## B. 安全红线（S 系列）— 违反即拒

### S-1 主密码、派生密钥、明文凭证永不写入磁盘
- **禁止**：`localStorage`、`chrome.storage.local`、IndexedDB、文件、日志文件。
- **允许**：`chrome.storage.session` 中的会话态；加密后的配置（不含明文凭证）。
- **验证**：CI 静态扫描 `localStorage` / `sessionStorage` / `storage.local` 的使用，白名单外 fail。

### S-2 禁止 console 输出任何凭证 / 密钥 / 含 token 的完整 URL
- **允许日志**：后端类型、成功 / 失败布尔、耗时、脱敏域名（eTLD+1）。
- **验证**：ESLint 禁直接 `console.*`，统一走日志封装函数；封装函数内做脱敏单测。

### S-3 往返后端强制 HTTPS
- **例外**：本地回环地址（`127.0.0.1` / `localhost`）用于 KeePassRPC 代理，须显式登记。
- **验证**：URL 构造集中在单一模块，CI 断言 scheme。

### S-4 内容脚本与页面上下文隔离
- **规则**：填充只通过 `input.value` + 派发 `input` / `change` 事件；禁止把凭证塞进页面 JS 可读的变量或 DOM 属性（如 `window.__vaultix`、`data-password`）。
- **理由**：页面脚本能读同一 DOM；写进去等于泄露给站点。
- **验证**：code review checklist + DOM 测试断言无敏感属性。

### S-5 剪贴板填充必须超时清空
- **规则**：默认 30 秒，用户可配置；复制密码后不得永久留在剪贴板。
- **验证**：测试用例（含定时器触发）。

### S-6 `source` 标记不可伪造
- **规则**：只有适配器层能写 `CredentialItem.source`；UI 与内容脚本只读。用 TS `readonly` 约束。
- **理由**：来源标记是冲突处理和用户信任的依据，被页面侧改写会造成错误填充。
- **验证**：类型系统 + 单测。

### S-7 遥测 / 错误上报默认关闭
- **规则**：默认 off；开启时 payload 不得含完整 URL、条目名、用户名，仅脱敏域名 + 错误码。
- **验证**：默认配置断言 + payload 脱敏单测。

### S-8 依赖锁定
- **规则**：`package-lock.json` 必提交；CI 用 `npm ci`；依赖更新走 PR 且人工看 diff。
- **验证**：CI 门禁。

## C. 许可证与上游代码（L 系列）

### L-1 本项目 GPL-3.0，新依赖必须 GPL 兼容
- **兼容**：GPL-2.0+、GPL-3.0、MIT、Apache-2.0、BSD
- **需评估**：LGPL（动态链接场景）、AGPL、SSPL、商业许可
- **禁止**：GPL-2.0 only（与 GPL-3.0 不兼容）
- **验证**：CI 依赖许可证检查。

### L-2 从上游摘录的任何代码，文件头必须标注来源
- **必含**：来源仓库、路径、commit、原许可证。
- **适用**：KeePassXC-Browser、bitwarden/clients、bw2keepass。
- **验证**：PR 模板勾选项 + code review。

### L-3 协议重新实现不得复制上游源文件
- **规则**：KeePassRPC 只依据公开协议文档实现，不 copy 上游 JS 文件。
- **理由**：协议实现与代码复制的法律性质不同；只照协议写可保持本项目代码独立性。
- **验证**：code review。

### L-4 LICENSE 文件不得删除或修改

## D. API 契约稳定性（C 系列）

### C-1 `CredentialItem` / `BackendAdapter` 是核心契约
- **规则**：任何字段增删改必须先改 `03-统一契约.md` 并经评审；变更伴随版本号 +1 与迁移说明。
- **禁止**在适配器之外直接构造 `CredentialItem`。
- **验证**：CI 检查契约文件 diff 触发人工审批；code review。

### C-2 后端差异不得泄漏到 UI 层
- **规则**：UI 只认统一模型 + `source`；后端特有信息放可选 `meta`，UI 必须能优雅降级（缺字段不崩）。
- **验证**：UI 单测用最小 `CredentialItem` 构造。

### C-3 新增后端必须实现完整 `BackendAdapter`
- **规则**：含能力声明 `capabilities`（如是否支持 TOTP / 写操作），不允许"半个适配器"；UI 按能力决定显示哪些操作。
- **验证**：接口实现完整性由 TS 类型系统保证 + 契约测试。
