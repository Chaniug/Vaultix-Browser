# 08 · 通行密钥（Passkey）

> 代码入口：`src/content/passkey-provider.ts`（页面主世界）、`src/content/passkeys-relay.ts`（中继）、
> `src/core/passkeys.ts`（编码与序列化）、`src/adapters/keepassrpc/adapter.ts`（线协议）。

## 1. 为什么要注入主世界

浏览器没有给扩展提供「通行密钥提供方」的官方接口。站点调用的是 `navigator.credentials.create/get`，
它们活在页面自己的 JS 上下文里——所以提供方必须作为**主世界脚本**接管这两个方法（Bitwarden、KeePassXC-Browser
都是这么做的），扩展的隔离世界只能通过 DOM 事件与它通信。

## 2. 流程

```
页面(主世界)                 中继(隔离世界)              后台              KeePassXC
credentials.create/get
   │ 序列化 WebAuthn 选项（二进制→base64url）
   ├─ CustomEvent ──────────►│
   │                         ├─ runtime message ────────►│
   │                         │                           ├─ passkeys-register/get ─►│ 校验域名、
   │                         │                           │                          │ 生成/签名
   │                         │◄────── 加密响应 ───────────┤◄──── response ───────────┤
   │◄──── CustomEvent ───────┤
   还原成 PublicKeyCredential 形状的凭据对象
```

两边的约定（依据 KeePassXC 2.8 源码，已对真实 KeePassXC 探测验证）：

| 方向 | 编码 |
|---|---|
| 发给 KeePassXC | `challenge` / `user.id` / `excludeCredentials[].id` / `allowCredentials[].id` 都是 **base64url** |
| KeePassXC 返回 | `attestationObject` / `authenticatorData` / `clientDataJSON` / `signature` 是**标准 base64**；`id`（凭据 id）是 **base64url** |

> 这两套编码弄反不会报错，只会静默失败，所以集中在 `src/core/passkeys.ts` 并用单测锁死。

## 3. 安全边界

- **origin 不由页面提供**：中继不传 origin，后台一律取消息发送者（该 frame）的 URL origin，
  再交给 KeePassXC 校验 rpId。页面即使伪造请求，也只能拿到自己域名下的凭据。
- **提供方不可用就完全回退**：未连接 / 未配对 / 版本过低时，直接调用原生 `navigator.credentials`，
  绝不因为装了扩展而弄坏站点登录。
- `mediation: 'conditional'`（条件式 UI）与 `'silent'` 不拦截。
- 浮层与中继都不持有私钥：通行密钥的密码学与存储全部在 KeePassXC 内完成。

## 4. 错误码

KeePassXC 的通行密钥错误有两种返回形态，适配器都会保留为 `{ errorCode }` 交给页面映射：

- 未加密的外层回复（实测 2.8.0：空公钥 → `errorCode: "24"`，非法 origin → `"25"`，且为字符串）；
- 加密响应里的 `response: { errorCode }`（用户在 KeePassXC 里取消等）。

页面侧映射为对应的 `DOMException`：域名类 → `SecurityError`；算法类 → `NotSupportedError`；
参数类 → `TypeError`；其余（含"未找到凭据""已取消"）→ `NotAllowedError`。

## 5. 版本门槛

`passkeys-*` 需要 KeePassXC ≥ **2.7.7**。版本来自 `change-public-keys` 响应的 `version` 字段，
解析失败一律视为不支持（宁可少开一个功能，也不向未知版本发不认识的请求）。

## 6. 实测记录（2026-11-25）

直连本机 `keepassxc-proxy.exe`，用已有配对（`valkjin`）执行：

| 请求 | 结果 | 说明 |
|---|---|---|
| `passkeys-get` + 空 publicKey | `errorCode 24`「空的公钥」 | 动作被正确路由（不是 7「Incorrect action」） |
| `passkeys-register` + 空 publicKey | `errorCode 24` | 同上 |
| `passkeys-get` + `http://` origin | `errorCode 25`「提供的 URL 无效」 | origin 校验生效 |

探测只用了会立即失败、**不写入任何条目、不弹窗**的请求。

## 7. 已知限制

- 返回的是**形状相同**的凭据对象（原型链指向 `PublicKeyCredential` / `Authenticator*Response`），
  不是浏览器原生实例。绝大多数站点只读字段，可以正常工作；严格做 `instanceof` 的站点会失败。
- 不支持条件式 UI（`mediation: 'conditional'`），这类请求交回浏览器。
- 注册时 KeePassXC 会自己弹窗让用户选择/确认，扩展不额外做用户确认。
- **Bitwarden 的通行密钥尚未支持**：KeePassXC 的路子是「扩展转发、KeePassXC 做密码学」，
  而 Bitwarden 需要扩展自己实现 WebAuthn 的密钥生成与签名，并把私钥按它的 Passkey 条目格式加密写回。
  这部分我无法在没有真实服务端的情况下验证，按项目一贯原则（协议必须对着真实服务验证）留到后续批次。
